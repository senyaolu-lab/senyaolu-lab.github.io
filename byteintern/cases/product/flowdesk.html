01 /

从一个问题，到一条可追踪的任务链。

问题假设：商家不会按“数据、素材、投放”这样的组织结构提问，而是直接说“为什么不赚钱了”。工作台需要帮助拆解任务，同时让用户知道系统正在做什么。

USER / ASSUMPTION

经营者需要结果，也需要掌控

假设使用者对经营目标清楚，却没有时间理解每个分析工具。首屏按业务任务组织入口；复杂过程留在计划和轨迹中，随时可查看。

CORE / CONTRACT

每一步都有输入与责任范围

快照提供事实，洞察定位变化，策略形成草案，负责人确认，执行模块归档。依赖顺序由状态机约束，界面不会让“待确认”伪装成“已完成”。

SUCCESS / TO VALIDATE

先证明任务可控

成功标准：计划顺序正确、失败后不重复副作用、未经授权无法归档、结果可以追溯。当前已做代码验证，尚未做目标商家可用性访谈。

02 /

让异常成为产品的一部分。

没有把“生成中”的动画当成 Agent 能力。重试、拒绝、取消和空结果，都拥有明确的界面与状态约束。

关键状态系统行为产品取舍
等待工具 / 运行中展示当前步骤、专家职责与工具名；只允许停止，不允许覆盖正在执行的任务。减少同时提交带来的状态混乱。多任务队列留到下一版本验证。
工具失败模拟洞察工具超时，保留上游快照，仅从失败步骤恢复；重试上限为一次。让恢复范围可理解。实际落地还需超时阈值、幂等键、退避与服务端持久化。
等待授权任务停在确认节点；展示动作、范围和后果，可审核结果后确认或拒绝。只有模拟归档需要确认，不反复询问无副作用的读操作。
拒绝 / 用户停止流程结束，后续工具不再执行；保留已完成步骤和事件记录供导出。当前停止是内存级状态切换。真实异步任务需取消令牌与正在执行请求的收尾语义。
任务完成结果必须带数据情景、指标、预算草案、限制与日志；新任务不会继承旧授权。当前为本地文件导出，没有长期存储或跨设备记录。
03 /

完成一条链路，也检查它如何失败。

与 GrowthPilot 共用数据与计算层。状态机测试验证人工确认门槛、拒绝终止、单步恢复、取消停止与授权不继承。

EVALUATION PLAN

三个层次，分别验收

① 规则层：用确定输入验证计算与状态转换。② 交互层：检查用户能否找到失败位置并完成重试。③ 模型层：未来接入 LLM 后，再评估任务分解、引用准确性与越权建议。

本次报告只包含已执行的规则层测试。未实施的用户测试、模型盲评与在线业务效果均不计入成绩。

LIMITS & NEXT

下一步要补的是运行基础

接入前先设计工具契约、幂等键、服务端授权、事件存储和审计。再用沙箱任务集验证系统恢复、工具异常与提示注入防护。

目前没有真实 LLM、外部 API、持久化任务队列或商家系统集成。输入目标只影响成本 / 收入策略优先级，其余计划来自固定工作流。
